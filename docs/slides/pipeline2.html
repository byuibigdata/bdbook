The tables to build, and how each one feeds the model

This page answers what to build — every box is a table a team has to materialise, with a grain, a schema and a job that writes it. For why each one looks the way it does — why the window is −15/+45, why three models, why the decision is priced against a no-offer world — read pipeline v1 → first.

The five Bronze tables are documented column by column in the data dictionary → — types, null rates, join keys and the traps.

Pick a table

Three layers, then serving:

Layer What it is
Bronze Exactly as PDI delivered it. Never edited
Silver Cleaned, typed, conformed. One row per real thing
Gold visit — the unit of analysis, and the label we built
Features Point-in-time, nothing knowable only after the pump
Serving What the pump sends, and what we must log back

The orange boxes are ours. visit is the one that matters: no column in the source data says “did they come inside?”, so we construct it, and every number downstream inherits whatever we got wrong.

What it costs to run

Table Rows Shape Notes
line_clean ~110M wide → narrow The expensive join. Broadcast master_gtin, it is only 99k rows
fuel_anchor 36.1M shuffle
store_tx 32.7M shuffle
visit 36.1M range join The one to watch — see below
feat_history ~216M window visit × 6 categories
als_interactions ~26M — Beverages only

Partition everything on date. transaction_items arrives as 19 undated files; rewrite it once as parquet partitioned by (dt) and every job below reads a slice instead of 3.8 GB.

The visit range join is the one that will hurt. A naive BETWEEN join has no equality key, so Spark falls back to a nested loop over 36.1M × 32.7M rows. Give it an hour-bucket equality key first — the window spans at most three buckets — then filter the exact minutes. That is the difference between minutes and never finishing.

Example conclusions. Row counts come from one run over the PDI extract — 940 stores in eight Intermountain West states, October 2024 to September 2026.

transaction_items

Grain: one row per item rung up. 128,599,042 rows.

Column Type Note
TRANSACTION_ITEM_ID decimal(38,0) Primary key. 22 digits — keep as string or decimal, Int64 overflows
TRANSACTION_SET_ID decimal(38,0) The basket key
STORE_ID decimal(38,0) Joins the store master
DATE_TIME timestamp Store wall-clock time, per PDI. No zone conversion needed
GTIN string 14-digit barcode; placeholder on keyed lines
UNIT_QUANTITY decimal(38,4) Gallons for fuel, count otherwise
GRAND_TOTAL_AMOUNT decimal(38,4) Tax-inclusive line total
SCAN_TYPE string GTIN | NONSCAN | PLU | FMT_ERR
NONSCAN_CATEGORY string NACS dept for keyed lines. FUEL lives here
NONSCAN_SUBCATEGORY string Fuel grade lives here 
items = spark.read.parquet("transaction-items-all/")

Every money column is Decimal(38, x). Cast once, early — decimal arithmetic in Spark is slow and the overflow rules will surprise you.

master_gtin

Grain: one row per barcode. 99,074 products, 35 PDI categories.

Column Type Note
GTIN string Primary key
CATEGORY string PDI’s taxonomy — not NACS
SUBCATEGORY string Finer split
BRAND string Monster, Red Bull, ZYN …
UPDATED_AT date All rows 2024-07-03 — a frozen snapshot 
gtin = (spark.read.parquet("master-gtin/")
        .select("GTIN", "CATEGORY", "SUBCATEGORY", "BRAND")
        .dropDuplicates(["GTIN"]))

Matches 88% of scanned lines. The master predates the transaction window, so anything launched since never matches.

shopper_id

Grain: one row per payment. 71,790,254 rows, 8.0M shoppers.

Column Type Note
PAYMENT_ID decimal(38,0) Primary key
TRANSACTION_SET_ID decimal(38,0) Not unique — split tender gives two rows
SHOPPER_ID string 32-char hash. Treat as PII 
shopper = (spark.read.parquet("shopper-id/")
           .select("TRANSACTION_SET_ID", "SHOPPER_ID")
           .dropDuplicates(["TRANSACTION_SET_ID"]))   # collapse split tender

SHOPPER_ID = hash(card BIN + last 4 + store state). The same card in two states is two shoppers, so anything cross-border is invisible, and a few ids collide onto more than one person.

stores_information

Grain: one row per store. 36,912 rows, of which 940 transact.

Column Type Note
STORE_ID decimal(38,0) Primary key
STATE, CITY, ZIP_CODE string Eight Intermountain West states in our 940
LATITUDE, LONGITUDE double Max longitude is exactly 180 — a placeholder
START_WEEK_CONTINUOUS_DATA date First week the store reports without gaps
CHAIN_SIZE decimal 1–386. Independents, not national chains 
stores = (spark.read.parquet("stores-information/")
          .select("STORE_ID", "STATE", "START_WEEK_CONTINUOUS_DATA"))

Filter on START_WEEK_CONTINUOUS_DATA before any time series, or stores joining the panel will read as growth.

discounts

Grain: one row per discount applied to a line. 17,429,831 rows.

Column Type Note
DISCOUNT_ID decimal(38,0) Primary key
TRANSACTION_ITEM_ID decimal(38,0) Many discounts per line — aggregate before joining
DISCOUNT_TYPE decimal 0 Mix&Match · 1 Combo · 2 Manager · 3 Loyalty · 4–5 Cashier · 6–8 Retailer · 9 Missing
DISCOUNT_NAME string Not standardised. ZYN and zyn are different values
DISCOUNT_AMOUNT decimal(38,4) Sign is inconsistent across promotions 
# Types 0,1,3,6,7 are real promotions. 2,4,5,8 are register overrides --
# a cashier fixing a price is not an offer anyone responded to.
PROMO_TYPES = [0, 1, 3, 6, 7]

Redemptions, not impressions. No row exists for an offer shown and declined, so P(buy | offered) is not computable from this table.

line_clean

Grain: one row per sellable line. ~110M rows after filtering.

Column Type Derivation
transaction_id string TRANSACTION_SET_ID cast to string
shopper_id string Joined from shopper_id
store_id int
ts timestamp DATE_TIME, store-local
category string coalesce(CATEGORY, NONSCAN_CATEGORY)
brand, gtin string Null on keyed lines
amount double GRAND_TOTAL_AMOUNT cast
fuel_grade string NONSCAN_SUBCATEGORY where category is FUEL 
line_clean = (items
    .withColumn("amount", F.col("GRAND_TOTAL_AMOUNT").cast("double"))
    .withColumn("qty",    F.col("UNIT_QUANTITY").cast("double"))
    .filter((F.col("qty") > 0) & (F.col("amount") > 0))      # drop 1.2M voids
    .join(gtin, "GTIN", "left")
    .join(shopper, "TRANSACTION_SET_ID", "inner")
    .withColumn("category", F.coalesce("CATEGORY", "NONSCAN_CATEGORY"))
    .filter(F.col("category").isNotNull()))

The two filters remove 481,568 voids and 701,406 returns. The coalesce labels 85.6% of lines — but it mixes PDI’s taxonomy with NACS, so reconcile FUEL/Fuel Products and LOTTERY/Lottery/Gaming before counting.

fuel_anchor

Grain: one row per fuel transaction. 36,142,617 rows. Each one is a moment when a pump screen could show something.

Column Type Note
fuel_tx string Primary key
shopper_id, store_id string, int
ts timestamp The moment the offer would fire
fuel_spend double Dollars, not gallons
fuel_grade string REGULAR, DIESEL, MID/PLUS, PREMIUM … 
fuel_anchor = (line_clean
    .filter(F.col("category") == "FUEL")
    .groupBy("transaction_id")
    .agg(F.first("shopper_id").alias("shopper_id"),
         F.first("store_id").alias("store_id"),
         F.min("ts").alias("ts"),
         F.sum("amount").alias("fuel_spend"),
         F.first("fuel_grade").alias("fuel_grade"))
    .withColumnRenamed("transaction_id", "fuel_tx"))

store_tx

Grain: one row per in-store transaction. ~32.7M rows. The candidate outcomes.

Column Type Note
store_tx string Primary key
shopper_id, store_id, ts
cats array<string> Distinct categories in the basket
skus array<string> Distinct GTINs
spend double Basket total 
NOT_A_PURCHASE = ["FUEL", "SERVICES"]        # SERVICES is 99.5% card fees

store_tx = (line_clean
    .filter(~F.col("category").isin(NOT_A_PURCHASE))
    .groupBy("transaction_id")
    .agg(F.first("shopper_id").alias("shopper_id"),
         F.first("store_id").alias("store_id"),
         F.min("ts").alias("ts"),
         F.collect_set("category").alias("cats"),
         F.collect_set("gtin").alias("skus"),
         F.sum("amount").alias("spend")))

Dropping SERVICES is the single most consequential filter here — it is card fees charged on the fuel sale itself, and counting it as a purchase inflated the attach rate by seven points.

visit

Grain: one row per fuel visit. 36,142,617 rows. The label lives here.

Column Type Note
fuel_tx string Primary key
shopper_id, store_id, ts From the anchor
fuel_spend, fuel_grade double, string
bought boolean The Model A label. 12.8% true
cats array<string> The Model B labels. Null when bought is false
store_spend double Median $7.87 when they buy 
BEFORE, AFTER = 15, 45       # minutes, asymmetric: most people fuel first

cand = store_tx.alias("s").join(
    fuel_anchor.alias("f"),
    (F.col("s.shopper_id") == F.col("f.shopper_id")) &
    (F.col("s.ts").between(F.expr(f"f.ts - INTERVAL {BEFORE} MINUTES"),
                           F.expr(f"f.ts + INTERVAL {AFTER} MINUTES"))),
    "inner")

visit = (fuel_anchor.join(
        cand.groupBy("fuel_tx").agg(
            F.array_distinct(F.flatten(F.collect_list("cats"))).alias("cats"),
            F.sum("spend").alias("store_spend")),
        "fuel_tx", "left")
    .withColumn("bought", F.col("cats").isNotNull()))

This column does not exist in the source data. The window is a judgement call, and it is the one a team has to defend: 77.2% of in-store purchases land within five minutes of the pump, and 16.2% happen before it.

feat_context

Grain: one row per visit. Everything knowable before the nozzle goes back — which is the leakage rule with a clock on it.

Column Type Note
hour int Attach spans 7.5% (2am) → 15.1% (6am)
daypart string morning 5–10 · midday 10–15 · evening 15–05
weekday, month int
store_id int High-cardinality — index it, don’t one-hot it
fuel_grade string Weak: 12.2%–13.3% across the big four
fuel_spend double Known mid-fill as gallons accumulate
store_base_rate double The store’s own attach rate, computed on train only 
daypart = (F.when(F.hour("ts").between(5, 9),   "morning")
            .when(F.hour("ts").between(10, 14), "midday")
            .otherwise("evening"))

feat_ctx = (visit
    .withColumn("hour",    F.hour("ts"))
    .withColumn("weekday", F.dayofweek("ts"))
    .withColumn("month",   F.month("ts"))
    .withColumn("daypart", daypart))

store_base_rate is a target encoding, so fit it on the training split alone or it leaks the label straight into the features.

feat_history

Grain: one row per visit × category. Point-in-time: only visits strictly before the one being scored.

Column Type Note
fuel_tx, category string Composite key
bought_before int Has this shopper ever bought this category?
prior_share double Share of their prior visits containing it
days_since int Since they last bought it. Null if never
prior_visits int 22.2% of visits have zero 
w = (Window.partitionBy("shopper_id", "category")
           .orderBy(F.col("ts").cast("long"))
           .rowsBetween(Window.unboundedPreceding, -1))   # <- excludes today

feat_hist = (exploded                     # visit x category, one row each
    .withColumn("bought_before", F.max("hit").over(w))
    .withColumn("prior_share",   F.avg("hit").over(w))
    .withColumn("days_since",
                F.datediff("ts", F.max(F.when(F.col("hit") == 1, F.col("ts"))).over(w)))
    .withColumn("prior_visits",  F.count("*").over(w)))

rowsBetween(unboundedPreceding, -1) is the whole trick. Drop the -1 and every row sees its own outcome.

History barely moves whether they come inside (12.6% with none, 12.5% with 10+), but it is the best signal for what they buy.

als_interactions

Grain: one row per shopper × SKU × daypart. The implicit-feedback matrix.

Column Type Note
shopper_ix int ALS needs integers, not hashes
item_ix int Index of "{gtin}@{daypart}"
n double Purchase count = confidence, not a rating 
inter = (store_tx_lines                       # before the scoring window only
    .filter(F.col("category") == "Packaged Beverages (Non-Alcoholic)")
    .withColumn("item", F.concat_ws("@", "gtin", daypart))
    .groupBy("shopper_id", "item").agg(F.count("*").cast("double").alias("n")))

idx = [StringIndexer(inputCol=c, outputCol=c + "_ix").fit(inter)
       for c in ("shopper_id", "item")]
als_interactions = Pipeline(stages=idx).fit(inter).transform(inter)

Why the daypart is in the key: same-daypart purchase pairs repeat the same SKU 18.0% of the time versus 10.0% across dayparts — 80% more likely. ALS takes no features, so the only way to give it a clock is to put one in the key.

Why it isn’t too sparse: 2.75M shoppers bought a beverage, 55% three or more times, averaging 16.2 purchases over 7.6 distinct SKUs.

train_a

Grain: one row per visit. 36.1M rows, one binary label. This is the table that goes into Model A.

CAT_COLS = ["daypart", "fuel_grade", "store_id"]
NUM_COLS = ["hour", "weekday", "month", "fuel_spend", "store_base_rate"]

stages = [StringIndexer(inputCol=c, outputCol=f"{c}_ix", handleInvalid="keep")
          for c in CAT_COLS]
stages += [OneHotEncoder(inputCols=["daypart_ix", "fuel_grade_ix"],
                         outputCols=["daypart_oh", "fuel_grade_oh"])]
stages += [VectorAssembler(
    inputCols=NUM_COLS + ["daypart_oh", "fuel_grade_oh", "store_id_ix"],
    outputCol="features")]

prep = Pipeline(stages=stages).fit(feat_ctx)
train_a = prep.transform(feat_ctx).select("fuel_tx", "features",
                                          F.col("bought").cast("int").alias("label"))

Split on time, not at random. A random split lets the model learn from next month to predict last month:

cut = "2026-04-01"
tr, te = train_a.filter(F.col("ts") < cut), train_a.filter(F.col("ts") >= cut)

store_id goes in indexed rather than one-hot — 940 levels is too many columns for a tree ensemble to spend splits on.

train_b

Grain: one row per converting visit. 4.6M rows, six binary labels — not one six-way label.

TOP6 = ["Packaged Beverages (Non-Alcoholic)", "Cigarettes", "Candy",
        "Salty Snacks", "Other Tobacco/Nicotine Products", "Beer"]

wide = feat_hist.groupBy("fuel_tx").pivot("category", TOP6).agg(
    F.first("prior_share"), F.first("days_since"), F.first("bought_before"))

train_b = (visit.filter("bought")
    .join(feat_ctx, "fuel_tx").join(wide, "fuel_tx"))

for cat in TOP6:                       # one label column per category
    train_b = train_b.withColumn(
        f"y_{slug(cat)}", F.array_contains("cats", cat).cast("int"))

Why six labels and not a softmax. A basket holds several categories at once — the six shares sum to 119%, not 100%. A multiclass model would force them to compete and hand back numbers that cannot be priced.

Category Share of converting visits
Packaged Beverages 54.5%
Cigarettes 14.7%
Candy 13.5%
Salty Snacks 13.1%
Other Tobacco 12.6%
Beer 10.5%

model_a

Will they come inside? One GBTClassifier plus a calibrator.

from pyspark.ml.classification import GBTClassifier

gbt = GBTClassifier(featuresCol="features", labelCol="label",
                    maxIter=120, maxDepth=6, stepSize=0.08,
                    validationIndicatorCol="is_val")   # early stopping
model_a = gbt.fit(tr)

scored = model_a.transform(te)        # -> probability: vector[2]
p_inside = F.udf(lambda v: float(v[1]), "double")
scored = scored.withColumn("p_inside", p_inside("probability"))

Do not rebalance the 12.8% positives. The output feeds an arithmetic in dollars; trained 50/50 an average visit scores 0.5 instead of 0.128 and every expected value inflates about 4×. Use weightCol if you must, never SMOTE.

Spark has no built-in calibrator, so fit isotonic regression on a holdout slice:

from pyspark.ml.regression import IsotonicRegression

cal = IsotonicRegression(featuresCol="p_vec", labelCol="label").fit(val)
p_cal = cal.transform(scored)         # <- the number the decision rule uses

Judge it on a reliability curve, not accuracy or F1. Calibration is the whole job.

model_b

Which category? Six independent binary models — binary relevance.

models_b = {}
for cat in TOP6:
    y = f"y_{slug(cat)}"
    models_b[cat] = GBTClassifier(featuresCol="features", labelCol=y,
                                  maxIter=80, maxDepth=5).fit(train_b_prep)

# Score every category for one visit, side by side.
out = train_b_prep
for cat, m in models_b.items():
    out = (m.transform(out)
            .withColumnRenamed("probability", f"p_{slug(cat)}")
            .drop("rawPrediction", "prediction"))

Each model returns a real probability for its offer, which is exactly the shape the decision needs — we are scoring six candidates, not picking one label.

GBT rather than logistic regression here because this is where the interactions live: beer on a Friday evening, coffee at 6am on a weekday.

model_c

Which SKU inside the category? ALS on implicit feedback.

from pyspark.ml.recommendation import ALS

als = ALS(userCol="shopper_ix", itemCol="item_ix", ratingCol="n",
          implicitPrefs=True,        # counts are confidence, not ratings
          rank=32, regParam=0.05, alpha=20,
          coldStartStrategy="drop", nonnegative=True)
model_c = als.fit(als_interactions)

top = model_c.recommendForUserSubset(live_shoppers, 20)   # 20 item_ix per shopper

Apply it per category, where the tail justifies it:

Category SKUs Top 100 covers Worth ALS?
Packaged Beverages 4,049 45.1% Yes
Candy 3,902 43.3% Yes
Cigarettes 1,311 85.9% No — show the best seller

Two ways to get it wrong. Fit only on interactions before the scoring window — ALS feels like preprocessing, which is why people forget. And coldStartStrategy="drop" silently removes unseen shoppers, so fall back to store-and-daypart popularity for them rather than returning nothing.

offer_catalog

Grain: one row per SKU the business will actually promote. This table does not exist — someone has to supply it.

Column Type Why it matters
gtin string
unit_margin double No cost column anywhere in the PDI data
discount double What the offer gives away
funded_share double 0–1: how much of it the brand pays
in_stock boolean Per store, per day 
offer_catalog = spark.read.table("murphy.offers")      # <- the ask

candidates = (top_skus
    .join(offer_catalog, "gtin")
    .filter("in_stock")
    # Funding is a share, not a flag. A brand often covers all of a
    # discount; sometimes the retailer and the brand split it.
    .withColumn("our_cost",
                (F.lit(1.0) - F.col("funded_share")) * F.col("discount"))
    .withColumn("effective_margin", F.col("unit_margin") - F.col("our_cost")))

Without unit_margin the expected-value rule cannot run at all — the arithmetic is in dollars and we have none of them. funded_share is what separates a profitable offer from a loss:

Brand funds Our cost Effective margin Uplift needed
100% $0.00 $1.30 any
50% $0.45 $0.85 +53%
0% $0.90 $0.40 +225%

At full funding the margin per unit is untouched and the store simply sells more volume, which is why these programmes exist at all. Inverted, the same arithmetic gives the minimum share to negotiate for — see negotiate.py.

score_request

Grain: one row per live fill, built at the pump in milliseconds.

Field Source Available?
shopper_id Card read before fuel flows Yes
store_id, pump_id Terminal Yes
ts Clock Yes
fuel_grade Grade selected Yes
gallons_so_far Live meter Yes
prior_* Feature store lookup by shopper_id Needs a feature store 
# Offline training and online scoring must share one transformer, or the
# features drift apart and nobody notices until the money is gone.
prep.write().overwrite().save("s3://.../prep_pipeline")

def score(req: dict) -> DataFrame:
    row = spark.createDataFrame([req])
    feats = prep.transform(row.join(feature_store, "shopper_id", "left"))
    return feats

The 90-second budget is the real constraint. Model A and the six Model B calls are cheap; the feature-store lookup is the latency risk, which is an argument for precomputing prior_* nightly per shopper.

decision

Grain: one row per candidate offer per fill. The arithmetic that picks one.

EPS = 0.01        # don't bother for less than a cent of expected margin

dec = (candidates
    .withColumn("p_buy",  F.col("p_inside") * F.col("p_category") * F.col("p_sku"))
    .withColumn("ev_offer", F.col("p_buy_with_offer") *
                            (F.col("unit_margin") - F.col("our_cost")))
    .withColumn("ev_none",  F.col("p_buy") * F.col("unit_margin"))
    .withColumn("uplift_value", F.col("ev_offer") - F.col("ev_none")))

best = (dec.filter(F.col("uplift_value") > EPS)
           .orderBy(F.desc("uplift_value")).limit(1))      # may return nothing

The naive form is wrong. P(buy) × margin − cost never compares against the world where no offer was shown, and it never goes negative while margin beats the discount. The real test is p₁(margin − discount) > p₀ × margin.

p_buy_with_offer is the honest gap: we do not have it. Without a holdout there is no p₁, only p₀, so today this rule runs on an assumed lift and should be labelled as such.

Returning nothing is a valid answer and costs nothing to execute.

decision_log

Grain: one row per fill where we could have shown something. This is the table that makes tomorrow’s model possible.

Column Why Recoverable later?
fuel_tx, shopper_id, ts Join key back to the visit Yes
candidates What we considered No
shown_gtin What we showed, null if nothing No
propensity The probability we showed it with No
is_holdout Whether this fill was held back No
model_version Which models produced it No 
(dec.select("fuel_tx", "shopper_id", "ts", "candidates",
            "shown_gtin", "propensity", "is_holdout", "model_version")
    .write.mode("append").partitionBy("dt").saveAsTable("gold.decision_log"))

Log the propensity or lose the ability to evaluate. Off-policy methods — inverse propensity weighting, doubly robust estimation — all need the probability with which each action was taken. If it was never written down, the information does not exist and no amount of later cleverness recovers it.

This log joins back to visit to produce the next training set, which closes the loop: the system’s own decisions become the data it learns from. That is also why the holdout matters — without it, the model only ever sees the consequences of what it already believed.
